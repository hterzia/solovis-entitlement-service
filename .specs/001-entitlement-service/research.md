# Phase 0 — Research

**Feature**: Entitlement Service (v1) | **Date**: 2026-08-09

Every `NEEDS CLARIFICATION` marker raised while drafting `plan.md` is resolved below, and every named dependency and integration is justified. Four questions could only be answered by the project owner; they were asked on 2026-08-09 and their answers are recorded verbatim in the relevant topics (§8, §14, §15, §9). **Zero markers remain in `plan.md`.**

---

## 1. Deployment topology

- **Decision**: A single Spring Boot management/storage service owns the SQLite file, the operator UI and all writes. Consuming product services do **not** call it on their hot path; each embeds a client SDK holding its own in-memory snapshot replica, refreshed from a delta feed. The service also exposes the §6 evaluation endpoints directly, for non-JVM callers, for the UI checker, and to satisfy criteria 25–26 as literally written.
- **Rationale**: The owner's requirement was explicit: *"i want a management/storage layer (this spring boot service) with a ui. then other services would be able to consume this service, with each service having a snapshot replica so that they are faster and could still survive if the management service layer is down."* This resolves three separate problems at once. It removes SQLite's single-writer limit from the availability story, because the read path never touches SQLite in any process. It makes the 5,000/s and 10 ms targets a non-issue, because the common case is an in-process map lookup. And it is the natural mechanism for the outage posture that spec §11 leaves to engineering — a replica that keeps answering is exactly "products carry on with the last answer they saw."
- **Alternatives considered**:
  - *Single service, every product calls it over HTTP for every decision.* Rejected: it makes the entitlement service a hard dependency in the request path of every product, and SQLite's single-writer nature means there is no second instance to fail over to. The outage posture would then have to be reimplemented, differently, in every caller.
  - *Writer plus read replicas of the SQLite file (WAL shipping / Litestream-style).* Rejected as unnecessary indirection: the replica the callers actually need is the domain snapshot, not the database file, and replicating the snapshot is smaller, simpler and language-agnostic over HTTP.
  - *Multiple service instances over one shared SQLite file on network storage.* Rejected outright — SQLite's locking is documented as unreliable over network filesystems, and this is where corruption comes from.

## 2. What gets replicated

- **Decision**: The SDK replicates the **model** — the capability registry, plan definitions, each account's plan assignment, and live overrides — not precomputed decisions. It then runs the identical `entitlement-core` resolver locally. The replicated model is an **answer-only projection**: overrides travel as `(account, capability, GRANT|HOLD, value)` and nothing more. Reason text, author and creation time are deliberately withheld from the feed.
- **Rationale**: Precomputing decisions would mean 100,000 accounts × ~500 capabilities ≈ 50 million answers, invalidated wholesale by a single plan edit. The model is small (§12) precisely because it is *compressed by structure* — 100,000 accounts share ~10 plans — so a plan edit is a delta of a few hundred bytes even though it changes every account on that plan.
  The projection is narrow because of a scope decision taken on 2026-08-09: *"only the main management/storage layer ui needs the explanation (§6.1), the rest of the services just need an answer."* Withholding the fields only a trace needs has three consequences, all good. Commercially sensitive reason text — "suspended pending investigation", "goodwill grant, renewal risk" — never leaves the management layer, which is the concern `future-spec.md` §11 raises about any surface beyond the operator UI. The feed and per-consumer memory both shrink by roughly half (§12). And criterion 24 gets stronger, not weaker: exactly one component can produce a trace, because exactly one component holds the record a trace is made of.
- **Alternatives considered**:
  - *Ship materialised per-account decisions.* The fair version of this is not 50 million rows but **one entitlement document per account** — ~100,000 blobs in a KV store, which is genuinely competitive because resolution then happens once, centrally, and drift becomes impossible. Rejected on two grounds: denormalising ~10 plans across 100,000 accounts turns a ~5 MB model into roughly 2 GB of documents, and a document store is a second piece of infrastructure to operate and keep available, which §11's posture would then depend on. Recorded here because the trade is real and the reasoning should survive the decision.
  - *Ship the full model including reasons, and let consumers build traces too.* Rejected after the 2026-08-09 scope decision — it replicates sensitive text to every process for a capability nobody outside the UI uses.
  - *Ship only what a caller asks for, cached per key with a 10 s TTL.* Rejected: it satisfies the 10 s reuse bound but not the outage posture, because a key never seen before has no last answer to fall back on.

## 3. Java version and build tool

- **Decision**: Java 21 (LTS), Maven multi-module reactor driven by the Maven Wrapper (`mvnw`).
- **Rationale**: Java 21 is what this host has (OpenJDK 21.0.11) and Spring Boot 4.0 requires at least Java 17 and supports up to Java 26, so 21 is comfortably inside the supported window. Neither Maven nor Gradle is installed here, so a wrapper is required either way; Maven's reactor is the least surprising way to express "one pure library consumed by both a service and a distributable client", and the SDK must publish clean, minimal POM metadata for other teams to depend on.
- **Alternatives considered**: *Gradle with the Kotlin DSL* — better multi-module ergonomics and faster incremental builds, rejected only because Maven's dependency metadata for a published client library is more predictable for consuming teams and the build here is not complex enough to earn Gradle. *Java 25* — not installed; adopting it would add a toolchain download for no feature this design needs.

## 4. Spring Boot version and web stack

- **Decision**: Spring Boot 4.0.x, Spring MVC on embedded Tomcat 11, **platform threads** with a tuned Tomcat thread pool. Virtual threads left off.
- **Rationale**: Verified against the Spring Boot documentation: 4.0 requires Java 17 minimum, is compatible through Java 26, and runs Servlet 6.1 on Tomcat 11.0.x. On threading, the documentation notes virtual threads want Java 21 or later with **Java 24+ strongly recommended**, and warns that pinning can *reduce* throughput. Our decision path performs zero blocking I/O — it is a handful of hash lookups and comparisons against an in-memory object graph — so virtual threads have nothing to unblock and would only add a pinning risk on Java 21. A modest platform pool sized to the machine is both faster and more predictable for a p99 target.
- **Alternatives considered**: *WebFlux* — rejected, reactive machinery buys nothing when there is no I/O to overlap and it makes p99 harder to reason about. *Spring Boot 3.5.x* — a fine fallback if a dependency lags on the 4.x line; recorded as the contingency, not the default.

## 5. Persistence access

- **Decision**: Spring's `JdbcClient` with hand-written SQL and explicit row mappers. No JPA, no Hibernate.
- **Rationale**: SQLite has no first-party Hibernate dialect, so JPA on SQLite means depending on a community dialect and fighting it over identity generation, `ALTER TABLE` limits and type affinity. More importantly, the entire hot path bypasses the database, so there is no object graph to lazily load and nothing an ORM would earn. The write path is a small, fixed set of statements that must each be paired with an audit record in the same transaction — explicit SQL makes that pairing visible.
- **Alternatives considered**: *Spring Data JPA + community SQLite dialect* — rejected for the dialect risk and for hiding the transaction boundaries that the audit trail depends on. *jOOQ* — genuinely attractive for type-safe SQL, rejected as an extra code-generation step and licence question for a schema this small.

## 6. SQLite configuration

- **Decision**: Xerial `sqlite-jdbc`; one file in WAL mode; `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`, `temp_store=MEMORY`. A **single** Hikari connection dedicated to writes plus a small read pool, all in the one management process.
- **Rationale**: WAL lets readers proceed while a write is in flight, which matters for the operator UI and for schema-driven admin reads even though decisions never touch the file. Restricting writes to one pooled connection removes `SQLITE_BUSY` as a class of bug rather than mitigating it with retries. `synchronous=NORMAL` under WAL is the standard durability/throughput trade-off and is safe against application crashes; only OS-level crash loss is traded, which is acceptable because a lost tail of writes is recoverable from the upstream systems that produced them. `foreign_keys=ON` matters because SQLite defaults it *off* per connection and the model leans on referential integrity.
- **Alternatives considered**: *`synchronous=FULL`* — rejected, unnecessary cost given write volume is operator-scale, not decision-scale, and the trade is revisitable in one property. *Rollback journal mode* — rejected, it blocks readers during writes.

## 7. Migrations

- **Decision**: Flyway, forward-only versioned SQL migrations under `db/migration`, run at startup by the management service (the only writer).
- **Rationale**: Flyway supports SQLite in the community edition and is auto-configured by Spring Boot, so this costs one dependency and one directory. Forward-only suits a schema whose audit table is append-only by construction. Because the service is the sole writer, running migrations at startup carries no coordination problem.
- **Alternatives considered**: *Liquibase* — equivalent capability, rejected only because its XML/YAML changelog abstraction obscures the SQLite table-rebuild recipe that some future migrations will need to express literally. *Hand-rolled versioning* — rejected; no reason to build what Flyway does.
- **Caveat carried into the migration strategy**: SQLite's `ALTER TABLE` supports little beyond adding a column and renaming. Any column drop, type change or constraint change must be written as the documented twelve-step recipe (create new table, copy, drop old, rename, rebuild indexes and triggers) inside one migration.

## 8. Meeting 5,000 decisions/s at p99 ≤ 10 ms

- **Decision**: All reads resolve against an **immutable snapshot** held behind an `AtomicReference`. A write builds version *N+1* by structural sharing — copying only the maps the change touches — and swaps the reference. Readers never lock, never block, and never observe a half-applied change.
- **Rationale**: A single-capability decision becomes a capability lookup, a plan-entitlement lookup, iteration over that account's (usually zero) overrides, and a comparison — microseconds, so the 10 ms budget is spent almost entirely in HTTP and JSON. A whole-account response over ~500 capabilities is still tens of microseconds of resolution plus 1–2 ms of serialisation, well inside 50 ms. Critically, this is also the answer to criterion 27 ("targets hold while plans and overrides are being changed"): because the snapshot is immutable and swapped atomically, a concurrent plan edit costs readers nothing at all — there is no lock to contend for and no cache to invalidate.
- **Two entry points over one rule**: `Resolver.resolve()` returns `(allowed, value)` and allocates nothing; `Resolver.explain()` runs the identical arithmetic and layers a `Trace` on top. Building a trace object graph for every decision at 5,000/s is pure garbage for answers nobody reads — the same reasoning §6.2 already applies when it excludes traces from whole-account responses. `resolve()` serves the SDK and the whole-account route; `explain()` serves the single-capability route, the checker and the plan-edit preview — which includes the criterion-25 load demonstration, since it runs against the single-capability route and therefore measures `explain()` with trace construction included (a few microseconds of the 10 ms budget — `contracts/decision-api.md` prices it). Because the arithmetic is shared rather than duplicated, a trace can never describe a different computation from the one that produced the value *(c24)*.
- **Alternatives considered**: *Query SQLite per decision with a Caffeine cache in front.* Rejected: it reintroduces invalidation (the hard problem this design deletes), and a cache miss storm after a plan edit is precisely the load spike criterion 27 forbids. *Materialise all decisions into a table and select them.* Rejected: 50 million rows rewritten by one plan edit. *One `explain()`-only resolver, discarding the trace when unused.* Rejected on allocation cost at the stated volume, and it makes the hot path's performance hostage to trace formatting.

## 9. Change visibility, read-your-writes, and the reuse bound

- **Decision**: The snapshot is rebuilt and swapped **synchronously inside the write transaction's commit path**, before the write's HTTP response returns, and a new `snapshot_version` row is published. SDK replicas poll `GET /v1/snapshot/version` every 5 s and fetch deltas. Budget: change committed and locally visible ≈ 0 s, replica converged ≤ ~6 s worst case, against a 60 s allowance.
- **Rationale**: Making the swap part of the write gives criterion 30 (an operator re-checking immediately sees their own change) for free, with no session affinity or read-your-writes token, because the operator's next request necessarily reads a snapshot that already contains the change. The 5 s poll keeps every SDK answer younger than the 10 s reuse bound in §7 under normal operation, so criterion 29 is satisfied structurally rather than by asking callers to behave. The generous margin to 60 s is deliberate — it leaves room for a replica to miss a poll or two without breaching the promise.
- **Relationship between the 10 s bound and the outage posture**: they conflict on purpose, and §11 wins. The 10 s bound applies while the service is reachable; during an outage the SDK knowingly serves an answer older than 10 s, because spec §11 fixes the posture that an outage must neither take away nor grant. The SDK surfaces this as an explicit `stale` flag and a snapshot age, so the breach is visible rather than silent.
- **Alternatives considered**: *Rebuild on a 30 s timer.* Rejected: fails criterion 30, and the operator would need a "wait and refresh" affordance the spec explicitly wants to avoid. *Server-Sent Events / long-poll push to replicas.* A better fit for freshness and worth revisiting, rejected for v1 because a 5 s poll of a single integer already lands ten times inside the requirement, and polling degrades more predictably during a partial outage.

## 10. Outage posture mechanism (spec §11, first item)

- **Decision**: Ship the Java client SDK. It keeps the last good snapshot in memory and, optionally, on disk so a caller restart during an outage does not lose it. On poll failure it keeps answering from that snapshot, exponentially backs off, and reports `stale=true` with the snapshot's age through `ClientHealth` and a metric. It **never** fails open and **never** fails closed. Direct HTTP callers get the same posture stated as an obligation, with `Cache-Control: max-age=10, stale-if-error=86400` and an explicit snapshot version header.
- **Rationale**: The owner chose to ship the SDK. It is the only way to *guarantee* the posture rather than document it: an outage that neither grants nor removes is a behaviour, and behaviours implemented independently by five product teams will differ. It also removes the largest correctness risk in the whole design — a product that fails closed during an outage takes capabilities away from paying customers, and one that fails open grants what was suspended.
- **Alternatives considered**: *Contract and documentation only.* Rejected by the owner; it leaves each caller to reimplement staleness and disk persistence. *Server-side last-known-good only.* Rejected as insufficient — it does nothing when the service is unreachable, which is the case the posture exists for.
- **Known limit, stated rather than hidden**: the SDK serves JVM callers. A non-JVM product calling the REST API must implement the posture itself against the documented contract; `contracts/java-client-sdk.md` states those obligations in language a port can follow.
- **The SDK returns answers, not explanations** (2026-08-09 scope decision). `check()` and `checkAll()` therefore return the same shape and a replica holds no trace **data** at all — the `Trace` type lives in `entitlement-core` and appears in the client only to deserialise the diagnostic path's response. A separate `explain()` method exists as a **diagnostic** path that always calls the service and never resolves locally — it is documented as unavailable during an outage and unsuitable for a request path, which is honest: an explanation requires the complete record, and the complete record lives in one place.
- **Read-through on an unknown account**: with a replica, "unknown account" is ambiguous — the account may not exist, or may have been created three seconds ago. Throwing at signup time would be a real defect, so before raising `UnknownAccountException` the SDK makes one bounded read-through call to the service and triggers an out-of-band poll. If the service is unreachable it throws, because inventing entitlements for an unknown account is exactly the granting §11 forbids.

## 11. Value modelling and the total order

- **Decision**: A sealed `EntitlementValue` with three variants — `Switch(boolean)`, `Quantity(long amount | unlimited)`, `Tier(key)` — carrying a per-type total order. `unlimited` is a **distinct variant**, not a sentinel number. Tier order is declared per capability in a `capability_tier` table with an explicit ordinal, and that ordinal is exposed to callers on every tier value.
- **Rationale**: §4's "most generous" and "most restrictive" are meaningless without a total order, and criterion 2 forbids expressing unlimited as a large number — which also rules out the tempting `Long.MAX_VALUE` shortcut, because it would leak into the API the moment a value is serialised. Criterion 3 requires the tier order to be visible to callers so "at least tier X" is answerable, which is why the ordinal travels with the value rather than living only in the registry. Sealed types let the resolver's comparison be exhaustively checked at compile time, so a fourth value type cannot be added later without the compiler pointing at every place that must handle it.
- **Alternatives considered**: *One numeric `rank` column covering all three types.* Rejected: it collapses "quantity 1" and "switch on" into the same storage, and forces unlimited to be a magic number. *Unordered choice values as a fourth type.* Explicitly out of scope, and no longer tracked as deferred scope either — it was withdrawn from `future-spec.md` on 2026-08-09. Every candidate examined (data residency, export formats, integrations, identity providers, cloud provider, billing currency) turned out to be a *set*, and a set is modelled cleanly as one switch per member. An unordered type would need its own resolution rule, giving up the total order that "most generous" and "most restrictive" depend on.

## 12. Snapshot footprint and feed size

- **Decision**: Hold the full model in heap; ship a full snapshot as gzipped NDJSON and incremental changes as deltas keyed by version.
- **Rationale**: Two sizings, because the management service and a replica now hold different things.
  *Management service* (full model, reasons included): 100,000 account assignments at ~120 B ≈ 12 MB; ~50,000 live overrides at ~200 B ≈ 10 MB; capabilities and plans negligible. Under 50 MB steady-state, under 100 MB during the double-buffered swap.
  *Replica* (answer-only projection, §2): overrides lose reason, author and timestamp, falling from ~200 B to ~40 B ≈ 2 MB. Around 25 MB steady-state. On the wire a full snapshot is roughly 5 MB raw and ~1 MB gzipped, fetched once at startup and never again unless the replica falls past the delta horizon. Deltas are typically a few hundred bytes.
  A 1 GB heap is comfortable in both roles, so the projection is a welcome saving rather than a load-bearing one — the reason for narrowing the feed is data governance (§2), not size.
- **Alternatives considered**: *Memory-mapped off-heap structures.* Rejected as premature at this size. *Per-tenant partial replicas.* Rejected for v1: it would need callers to declare which accounts they serve, which none of them can do statically.
- **Assumption flagged**: 500 capabilities and 50,000 overrides are estimates. The spec fixes only the account count. If capabilities reach the low thousands the sizing is still fine; if live overrides reach the millions, revisit before building.

## 13. Recording a plan's past values (spec §11, second item)

- **Decision**: Keep one mutable current row per plan capability value. A plan's history is reconstructible by replaying the append-only audit trail, which records before and after for every edit. No `plan_version` table.
- **Rationale**: §3.2 settles the business rule — a plan edit applies to everyone on the plan — and §8 explicitly forbids plan rollback, giving the reasoning: accounts move between plans in the meantime, so replaying an old version can grant capabilities to accounts that were never meant to have them. A version table would therefore be write-only data whose only obvious use is the button the spec forbids. The audit trail already satisfies every stated requirement: criterion 32 (before/after, actor, timestamp), criterion 33 (filterable, retained 24 months, never edited).
- **Alternatives considered**: *Full bitemporal plan versioning.* Rejected as building the substrate for a feature that was deliberately deferred. `future-spec.md` §4 records the consequence of this decision for that item: versioning does **not** fall out of the record-keeping choice and must be built deliberately if it is ever wanted. Nothing here blocks it, and the audit trail is the material it would be built from — every edit carries before, after, actor, time and affected-account count, which is enough to reconstruct any past state. *Snapshot the whole plan on each edit into the audit row.* Partially adopted — the audit `before_json`/`after_json` carry the changed entitlements, which is what reconstruction needs, without a second source of truth for the current value.

## 14. Operator identity and roles

- **Decision**: **Deferred at the owner's instruction.** The service defines an `ActorResolver` interface returning an actor identity and kind (`PERSON` / `SYSTEM`) plus a source, and ships a `StubActorResolver` bound to a configured development identity. Endpoints are not authenticated and roles are not enforced.
- **Rationale**: The owner's answer was *"for now its just me testing it out, we will add user compatibility later."* The seam exists so that audit completeness (criteria 32 and 36) is designed in from the start and so that adding OIDC later is a bean replacement rather than a retrofit through every controller — actor and source are already threaded into every write path and every audit row.
- **Alternatives considered, for when this is picked up**: *OIDC/SSO with roles from a group claim* — the likely destination, needs an identity provider named. *Local accounts in SQLite with Spring Security form login* — self-contained, viable if no IdP is available. *Trusted headers from a gateway* — least work, but moves the whole security boundary somewhere this plan cannot verify.
- **Consequence, stated plainly**: acceptance criterion 37 cannot be demonstrated. Until authentication lands, the service must not be reachable from an untrusted network, because anyone who can reach it can lift a compliance HOLD — an escalation of the risk `future-spec.md` §2 already flags, and the reason that item now names operator sign-in as a hard prerequisite.

## 15. Operator UI stack

- **Decision**: React 19 + TypeScript + Vite, TanStack Router and TanStack Query, styled from the canonical `.claude/design/solovis/tokens.css`. Built by npm, output copied into the service's `static/` so there is a single deployable and no CORS configuration.
- **Rationale**: The owner chose "react spa + rest". TanStack Query fits the five screens well — the checker, the account view and the plan-edit preview are all read-heavy views over the same admin API, and its cache invalidation on mutation is what makes criterion 30 visible in the UI. A repository-canonical token file already exists and forbids contradicting values, so the SPA imports it rather than restating colours.
- **Alternatives considered**: *Server-rendered Thymeleaf.* Rejected by the owner; it would have given read-your-writes and the single toolchain for free, but not the interaction density the plan editor and capability tree need. *A component library (MUI, Ant).* Rejected — it would fight the Solovis token system; the five screens need a small set of purpose-built components instead.
- **Design constraint carried forward**: the trace renderer must display the trace object the API returned, without recomputation or re-wording (criterion 24). `TraceView` takes the response payload and renders it; it must not derive anything.

## 16. Capability grouping and search at scale

- **Decision**: Store a derived `area` column (the capability key's prefix before the first dot) and index `(area, status)`. The registry and plan editor render a collapsible tree by area with client-side search; the admin list endpoint also accepts `area` and `q` filters for server-side narrowing.
- **Rationale**: Criterion 40 and §9 require grouping with collapse and search, and the spec is explicit about why — modelling sets as one switch per member means a twelve-region residency set is twelve capabilities, and a few hundred capabilities is a plausible steady state. Deriving and storing the area rather than parsing at read time keeps the affected-count and plan-editor queries index-served.
- **Alternatives considered**: *Free-form tags.* Rejected — the spec's grouping is the key's own namespace, and a second taxonomy would drift from it. *Parse the prefix on every read.* Rejected as unindexable.

## 17. Audit append-only enforcement

- **Decision**: `audit_event` carries `BEFORE UPDATE` and `BEFORE DELETE` triggers that `RAISE(ABORT)`, alongside an autoincrement sequence used as the service's logical clock.
- **Rationale**: Criterion 33 requires history that can be added to but never edited or removed. Enforcing it in the schema means it holds against an errant migration, a future feature, and a hand-typed statement — not merely against well-behaved application code. The same sequence gives snapshot versions a monotonic anchor, so "the state as of audit sequence N" is a well-defined moment (criterion 31).
- **Alternatives considered**: *Application-layer discipline only.* Rejected — the guarantee is the point. *Hash-chained records.* Rejected as tamper-*evidence* aimed at a threat model (a malicious operator with file access) that v1 does not claim to address; recording it here as the natural upgrade if that threat becomes real.
- **Retention**: 24 months is a floor, and the audit table is the only unbounded grower. No pruning job in v1; a rough estimate at operator-scale write volume keeps it well inside SQLite's comfortable range, and the plan records this as something to measure rather than assume.

## 18. Demonstrating the volume criteria

- **Decision**: k6 run from the `grafana/k6` Docker image (Docker 29.1.4 is present; k6 is not installed and this avoids installing it). Four scenarios: sustained single-capability load, a separately measured whole-account scenario, a concurrent write-churn generator, and a freshness probe that writes a known change and measures when it becomes visible at both the service and an SDK replica.
- **Rationale**: The spec's definition of done is unusually specific — criteria 25–31 must be evidenced *against data that is changing during the demonstration*. That makes the churn generator a first-class part of the harness, not a nicety, and it is why criteria 25 and 26 are measured in separate scenarios (criterion 26 says so explicitly). The freshness probe is the only way to evidence criterion 28 end to end rather than assert it.
- **Alternatives considered**: *Gatling* — JVM-native and would share the model classes, rejected because the harness must exercise the deployed HTTP surface from outside, and k6's scenario/threshold model expresses "p99 under X while Y churns" more directly. *JMH microbenchmarks alone.* Rejected — they would prove the resolver is fast and prove nothing about the requirement.
- **Prerequisite**: a seeder that creates 100,000 accounts, ~500 capabilities across ~15 areas, ~10 plans and ~50,000 overrides, so the demonstration runs at the stated scale rather than a convenient one.

## 19. Testing approach

- **Decision**: JUnit 5 + AssertJ throughout; **jqwik property-based tests** on `entitlement-core` asserting that resolution is invariant under permutation of the override set and repeated evaluation; Spring integration tests against a temp-file SQLite database; SDK tests against a stubbed feed covering outage, stale service and forced full-resync; Vitest + Testing Library for components; Playwright for the five screens.
- **Rationale**: Criteria 12, 13 and 16 are order-independence claims, and order-independence is exactly what example-based tests are worst at — a property test that shuffles the overrides and asserts an identical decision tests the actual claim. The §5 worked-examples table is a ready-made parameterised test fixture and should be transcribed literally, so that the specification's own examples are executable. Those same examples are then reused as conformance vectors (§20), so one fixture serves both the build and the runtime drift gate.
- **Additional obligation**: every test that asserts a value must also assert that `resolve()` and `explain()` agree. The two entry points share their arithmetic by construction, but a test that pins it makes the sharing a checked property rather than a code-review observation.
- **Alternatives considered**: *In-memory SQLite for tests.* Rejected — it differs from the deployed configuration in WAL behaviour and file locking, and a temp file costs nothing. *Testcontainers.* Not applicable; there is no server to containerise.

## 20. Guarding against resolver drift across replicas

- **Decision**: `entitlement-core` declares a `RESOLVER_CONTRACT` integer, bumped whenever resolution semantics change. The service publishes that number and a set of **conformance vectors** — self-contained `(model fragment → expected allowed, value)` cases — on the snapshot feed. Every replica evaluates the vectors against its own engine at startup and **refuses to serve** on any mismatch or unknown contract number, rather than starting and quietly disagreeing.
- **Rationale**: This design puts the resolution rule in every consuming service, which is §1's scattered-logic failure reappearing one layer down: two products on different SDK versions could return different answers for the same account. The wire `format` integer guards the payload shape, not the semantics, so something else has to guard those. Vectors are the cheap option because the spec already wrote them — §5's worked-examples table is a conformance suite, and generated cases extend it. The risk is dormant today because §4's rule is small and frozen by 41 criteria; it becomes live the moment `future-spec.md` §1 (time-bounded overrides) or §3 (relative grants) redefines "most generous", which is exactly when a gate needs to already exist rather than be retrofitted.
- **Why this matters more now that consumers have no traces**: with the answer-only projection (§2), a disagreement cannot be diagnosed after the fact by diffing two explanations — the SDK has none to diff. Detection therefore has to be proactive at startup, with the operator UI's checker as the reactive diagnostic surface. Every replica also reports its contract number and snapshot version as metrics, so a partial rollout is visible before it is a support ticket.
- **Alternatives considered**: *Semantic versioning discipline on the SDK artifact.* Rejected as the sole control — it depends on every consuming team upgrading promptly, which is precisely the assumption that fails. *Refuse to serve replicas below a minimum SDK version, enforced server-side.* Weaker: it tests a version string rather than actual behaviour, and it cannot catch a build that reports the right version and behaves wrongly. Worth adding later as a second layer. *Signed snapshot bundles*, as OPA does for policy bundles — a good idea for a different threat (tampering in transit) and recorded as the natural next step once the service leaves a trusted network.

## 21. Read-your-writes across service boundaries

- **Decision**: Every mutating admin response returns its resulting `snapshotVersion`, and both the SDK and the `/v1` routes accept a `minSnapshotVersion`. A caller that supplies one gets an answer resolved at or above that version, or a `409 entitlement/snapshot-behind` carrying the replica's current version.
- **Rationale**: Criterion 30 is scoped to the operator UI, and the synchronous snapshot swap (§9) satisfies it there. It says nothing about the cross-service case, which is real: billing reassigns a plan and immediately calls a product API whose replica is up to 5 seconds behind, so the product answers on the old plan. Passing the version forward turns "probably caught up by now" into a checkable condition. This is the Zanzibar *zookie* pattern in its cheapest possible form — a monotonic integer instead of an opaque consistency token, which suffices because there is a single writer and therefore a single global order.
- **Alternatives considered**: *Do nothing and rely on the 60-second bound.* Defensible, since the spec only promises 60 seconds — rejected because the failure is silent and lands on the customer-visible path immediately after an upgrade, which is the worst moment. *Block inside the SDK until the replica catches up.* Rejected as a default: turning a microsecond lookup into a multi-second wait is a bad trade to make implicitly; offered as an opt-in `awaitVersion(timeout)` instead. *Opaque tokens.* Rejected as unnecessary machinery for a single-writer system.
